## 2026-11-14 内存复测

测试设备：Apple M5，macOS 26.6，arm64。使用 `./scripts/build.sh` 默认优化构建 `0.1.0-memory-preview`，原生代码基线 `d6417d5`。依赖以 `clients/nsgo/go.mod` 为准。

应用以 `AGENTHUB_NSGO_DEMO=1` 和独立数据目录启动，不连接真实 Agent。启动约一分钟后采样；每个场景 5 次，间隔 2 秒。会话场景加载演示 Markdown、代码块、表格与两条消息，未传输附件。

| 场景             | 物理占用中位数 | RSS 中位数   | 本次物理占用峰值 |
| ---------------- | -------------- | ------------ | ---------------- |
| 演示本机面板空闲 | 约 39.5 MiB    | 约 123.5 MiB | 约 39.5 MiB      |
| 打开演示会话     | 约 48.4 MiB    | 约 137.5 MiB | 约 48.4 MiB      |

这两个复测场景的**物理占用都低于 100 MiB**；不能把它改写成所有平台、所有工作负载的上限。

### 为什么之前显示约 119 MiB

之前记录的是另一次演示构建的 **RSS**，5 次样本中位数 118.9 MiB。RSS 与 macOS `vmmap` 的 **Physical footprint** 不是同一个指标：RSS 包含驻留共享映射，不能直接等同于活动监视器“内存”的核算口径。Physical footprint 更接近系统按进程核算的物理内存负担，还涉及压缩等统计，不能简单把两者相减当成精确的共享内存。

本次面板 RSS 样本为 126480、126496、126512、126512、126512 KiB，物理占用为 39.4、39.4、39.5、39.5、39.5 M；会话 RSS 为 140208、140656、140752、140752、140800 KiB，物理占用为 47.9、48.3、48.4、48.4、48.4 M。这里保留 `vmmap` 原始 M 输出，表格按约 MiB 展示；MB 用于十进制文件体积。

### 场景限制

只测 Reign 应用进程，不包含独立的 Codex app-server、Agent 或模型进程。真实长会话、图片、窗口、网络与缓存会增加占用。作为旁证，机器上另一个旧 RAS 客户端运行约 9.5 小时后物理占用约 100.8 M；旧构建与真实环境不可直接横向比较，但说明空闲演示不是长期使用保证。

## 复现

```sh
cd clients/nsgo
./scripts/build.sh macos_arm64 -output /tmp/reign-measure -version 0.1.0-memory-preview
AGENTHUB_NSGO_DEMO=1 AGENTHUB_NSGO_DATA_DIR=/tmp/reign-measure-data \
  /tmp/reign-measure/Reign-0.1.0-memory-preview-macos_arm64/Reign.app/Contents/MacOS/Reign
```

保持测试进程运行，用另一终端记录它的 PID 后，分别读取：

```sh
ps -p PID -o rss=
vmmap -summary PID
```

`ps` 的 macOS RSS 单位为 KiB。`vmmap` 头部列出 Physical footprint 和本次进程峰值；不要把末尾映射表包含共享库的总量当成应用独占内存。采样前记录是否前台、页面内容和等待时间，不要混入开发工具或真实 Agent。

## 为什么选择原生 UI

NSGo 使用平台原生视图，不打包 Chromium／WebView 运行时。Go 核心与 UI 在同一应用进程内工作，消息采用虚拟列表和增量更新。这些设计减少运行时层次，但不代替真实长会话、附件、直连与中继场景的持续性能测试。
